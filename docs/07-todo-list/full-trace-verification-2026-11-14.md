# 전체 기록 재생 최종 검증

이 문서는 전체 기록 복원부터 발표용 요약 개선까지의 단계별 이력이다. 각 절의 수치와 로컬·PR 상태는 검사 당시를 뜻한다. 현재 기능·최신 테스트 수·검증 한계는 [최종 종합 QA](final-qa-2026-11-14.md)를 기준으로 한다.

## 원인과 수정

앞선 수정은 전체 수학적 탐색만 완료하도록 바꾸고, 전체 보기에는 여전히 처음 80,000개 이벤트만 전달했다. 사용자가 요청한 전체 탐색 재생을 충족하지 못했다.

현재 웹 전체 보기는 80,000개 버퍼에 제한되지 않는다. 실제 실행 기록을 200개씩 구간 조회하며, 단계 번호 입력과 마지막 단계 이동을 지원한다. 다음·이전·자동 재생은 구간 경계를 넘어 이어지고, 마지막에 다시 재생하면 처음부터 시작한다. 요약은 별도로 유지한다.

서버는 실제 실행의 문제·해·종료 상태·이벤트 수를 보관한다. 초기 스냅샷 버퍼 밖의 기록은 같은 결정적 실행 순서를 복원한다. 완전탐색은 부분 트리의 이벤트 수를 이용해 목표 위치로 직접 접근하며, 실제 실행이 도달한 범위를 넘는 가상 기록을 제공하지 않는다. 작은 문제의 전체 원본 기록과 복원 기록을 모든 필드에 대해 비교했다.

## 실제 브라우저 확인

SEND + MORE = MONEY → 완전탐색 → 풀이 시작 → 전체 보기에서 직접 확인했다.

| 조작 | 확인한 화면 |
|---|---|
| 전체 보기 진입 | `1 / 7,748,195`, 기록 제한 경고 없음 |
| 80001 입력 후 이동 | `80,001 / 7,748,195`, 실제 복귀 이벤트 표시 |
| 마지막 단계 이동 | `7,748,195 / 7,748,195`, 실제 finish 이벤트 |
| 마지막 결과 | 탐색이 끝났습니다 / 9567 + 1085 = 10652 |

마지막에서 다음 버튼은 비활성화되고 이전·다시 재생은 가능하다. 확인 중 콘솔 오류는 없었다. [실제 마지막 화면](verification-assets/full-trace-last.png).

추가로 실제 브라우저에서 200단계에서 자동 재생을 시작하고 202단계까지 진행되는 것을 확인했다. 페이지 경계에서 재생이 종료되지 않았으며, 정지 후에도 다음·이전 버튼이 활성 상태였다.

## 회귀 검증

- Python **34개 통과**: Core·API·통합과 아카이브 검증 포함.
- UI **32개 통과**: 페이지 경계의 200→201 이동, 실제 마지막 단계, 마지막에서 재생 재시작 포함.
- 네 개의 작은 수식을 두 알고리즘으로 실행해 복원 기록 전체와 원본 이벤트를 일대일 비교. 배정·순번·깊이·수식 검사·이유·복귀·정답 표시 모두 일치.
- 해 개수 제한으로 중단된 실행도 도달한 이벤트까지만 복원되는지 검증.
- 기본 SEND 완전탐색이 유효 완성 배정 1,451,520개를 검사하고 완료하며, 원본 버퍼 이후와 마지막 종료 이벤트를 조회하는 API 검증.
- JavaScript 문법과 diff 공백 검사 통과.

## 남은 조건

기록은 최근 4개 실행, 실행별 10분 동안 조회하며 만료 시 다시 풀이가 필요하다. 백트래킹의 대규모 버퍼 밖 후반 조회는 앞에서부터 결정적으로 재생하므로 위치가 깊으면 응답이 느려질 수 있다. 자동 재생 중 구간을 가져오는 동안 짧게 기다릴 수 있다. 이미 끝난 수백만 단계를 한꺼번에 내려받거나 브라우저 메모리에 올리지는 않는다.

풀이 시간·해 수 제한은 그대로 적용되며 중단된 실행을 완료로 표시하지 않는다. 레거시 API의 즉시 전체 버퍼 반환은 호환 목적으로 유지하며, 웹 전체 보기는 페이지 API를 사용한다. 변경은 아직 로컬 작업 상태이며 PR·병합은 진행하지 않았다.

## 후속 수정: 전체 예제의 요약 흐름과 재생 속도

아래는 첫 번째 요약 개선 당시의 이력이며, 후보 연결 오류에 대한 최종 수정은 마지막 절을 기준으로 한다.

모든 예제와 두 알고리즘의 요약에 연속 장면 구성을 적용했다. 초기 배정·검사, 다른 후보의 실패·복귀, 정답 발견과 남은 후보 검사, 종료를 구분한다. 장면 전환과 정답·종료 직전 자동 재생을 멈추고 다음 장면 버튼으로 이어간다. 생략한 단계 수와 변경될 배정을 미리 안내한다. 1×에서 배정은 1초, 계산·올림·충돌·가지치기·전체 식 검사·정답은 1.5초 유지하며 속도 선택을 반영한다. 전체 보기의 모든 단계 접근은 유지한다.

실제 SEND 비교 화면에서 백트래킹은 113단계, 완전탐색은 117단계 요약을 확인했다. 백트래킹 24단계에서 다음 장면으로 넘어가기 전에 중간 생략 수와 `D 0→3, E 3→5`를 안내하며 멈췄다. 완전탐색도 28단계에서 독립적으로 멈추고 바뀔 배정을 안내했다. 콘솔 오류는 없었다. [실제 요약 장면 전환](verification-assets/summary-scene-all.png).

최종 자동 검증은 Python **34개**, UI **35개** 통과. 예제 5개×알고리즘 2개에서 생략 구간의 정지·수동 이동·종료를 확인했고, 정답과 종료를 서둘러 공개하지 않는 동작, 요약의 표시 시간, 마지막 확인 후 자동으로 처음부터 재생되지 않는 동작도 검증했다. 실제 기록 순서와 스냅샷을 보존하며 장면 사이의 모든 시도를 표시하는 것은 아니므로 전체 구간이 필요하면 전체 보기를 사용한다.

## 최종 수정: 서로 다른 후보의 계산과 올림이 연결되던 오류

사용자 스크린샷에서는 97단계의 자리 계산과 98단계의 자리올림 사이에 B·I·L이 모두 바뀌었다. 앞선 속도 조정과 생략 안내는 이 오류를 해결하지 못했다. 임의의 중간 기록 조각을 붙이는 요약을 제거하고, 대표 실패 분기를 숫자 해제까지 보여 준 다음 첫 정답에 도달한 실제 배정 경로를 따라가도록 바꿨다.

검증 조건은 인접 요약 단계의 배정 변화가 해당 배정/복귀 이벤트 하나로 설명되는 것, 계산과 자리올림이 같은 배정·자리·연속 원본 순번을 갖는 것, 정답 이후 다른 실패 후보가 끼어들지 않는 것이다. 이 조건의 회귀 테스트는 수정 전 실패했고 수정 후 통과했다.

실제 브라우저의 I + BB = ILL 요약에서 9/25는 B=2·I=1·L=3의 두 번째 자리 계산, 바로 다음 10/25도 같은 배정의 자리올림이었다. 이후 충돌·숫자 해제·새 배정으로 이어지고 25/25에서 1 + 99 = 100으로 종료했다. [계산 화면](verification-assets/same-candidate-calculation.png)과 [바로 다음 올림 화면](verification-assets/same-candidate-carry.png)을 비교할 수 있다.

SEND 비교도 실제 화면에서 양쪽의 모든 다음 단계를 눌러 확인했다. 백트래킹 38단계, 완전탐색 26단계 요약이며 두 계산판 모두 9567 + 1085 = 10652로 끝났다. 계산/올림 사이 후보 혼합과 정답 이후의 다른 후보 끼워넣기는 없었고 콘솔 오류도 없었다.

최종 검증: Python **36개**, UI **35개** 통과. 기본 예제 5개×두 알고리즘과 추가 수식 20개×두 알고리즘의 요약에서 후보 변화의 인과관계를 검증했다. 초기 단계에서 장면 전환을 기다리는 중에도 재시작/이전으로 전환 대기를 취소할 수 있다. 전체 보기의 모든 기록 접근 기능은 유지한다. PR·병합은 아직 진행하지 않았다.

## 예제 전환 시 이전 수식이 섞이는 오류

원인: 같은 계산판 DOM에 새 재생기를 만들 때 이전 재생기의 버튼 이벤트 연결을 제거하지 않았다. I + BB = ILL 이후 SEND를 실행하고 재생을 누르면 이전 문제와 새 문제의 타이머가 함께 살아나 계산판을 덮어썼다. 기존 검증은 문제별 새 DOM 사용이 중심이라 같은 탭에서 문제를 연속 전환하는 수명 주기를 놓쳤다.

수정: 재생기별 AbortController로 고정 컨트롤 이벤트의 수명을 관리하고 destroy에서 일괄 해제한다. 종료된 재생기는 재생·이동·렌더링과 타이머 콜백을 다시 수행하지 않도록 방어한다. 네트워크 응답에 대한 기존 세대/종료 검사는 유지한다.

회귀 테스트는 수정 전 단일 패널에서 재생 타이머 2개로 실패했고 수정 후 1개로 통과했다. 같은 DOM에서 I + BB = ILL과 SEND를 반복 선택하고 백트래킹·완전탐색·비교를 모두 전환하는 검증을 추가했다. 각 타이머 진행 후 계산판 문자들이 현재 수식과 정확히 일치하고, 활성 타이머가 현재 패널 수를 넘지 않는지 확인한다. UI 전체 **37개 통과**.

실제 브라우저에서도 같은 탭에서 예제를 반복 전환했다. SEND 단일 패널은 SENDMOREMONEY만, SEND 비교는 양쪽 모두 SENDMOREMONEY를 유지했으며 두 패널 끝에서 9567 + 1085 = 10652를 표시했다. 콘솔 오류는 없었다. [예제 전환 후 실제 화면](verification-assets/example-switch-fixed.png). 기존에 열린 탭에는 수정된 스크립트를 적용하기 위해 한 번 새로고침이 필요하다.

## 발표용 장면 요약

기본 보기를 발표용 요약으로 바꾸었다. 실제 이벤트를 문제·배정·실패·복귀·재시도·대표 자리 계산·정답·종료의 약 6~10개 장면으로 구성한다. 기존 상세 요약은 단계별 요약, 모든 기록은 전체 기록으로 유지한다. 장면마다 큰 제목, 한 문장 설명, 실제 숫자 계산식, 발표 포인트를 제공한다. 번호 목차와 이전/다음 장면, 좌우 방향키로 수동 진행하며 자동 재생은 선택 사항이다. 1×에서 장면당 약 6초다.

서버는 presentation_scenes 배열에 실제 앵커 이벤트와 설명을 반환한다. 자리 계산은 앵커의 숫자·올림으로 생성하며 결과 문자가 배정된 실제 이벤트를 사용해 결과 숫자도 계산판에 보인다. 제한 중단은 완료라고 설명하지 않는다. 첫 장면부터 마지막 답을 미리 보여 주지 않도록 발표 모드에서는 외부 결과 목록을 접는다.

SEND 비교를 실제 1280×720에서 확인했다. 백트래킹 10장면, 완전탐색 7장면이며, 일의 자리 장면에서 7 + 5 = 12, 결과 숫자 2, 다음 자리 올림 1을 표시한다. 계산판의 Y에도 실제 배정된 2가 보인다. 양쪽 패널 하단은 약 701px로 화면 안에 들어왔다. 375×812에서는 세로 배치되며 페이지 가로 너비는 375px였다. 콘솔 오류는 없었다. [발표용 SEND 장면](verification-assets/story-send-math.png), [모바일 배치](verification-assets/story-mobile.png).

자동 검증: Python 전체 38개, UI 전체 40개 통과. 마지막 문구·결과 숫자 표시·키보드 포커스 수정 후에는 발표 장면의 수학과 앵커 검증 2개, 발표 UI 검증 4개를 추가 재실행해 통과했다. 기존 UI 회귀 테스트는 단계별 요약/전체 보기를 명시적으로 선택하고, 신규 테스트는 실제 기본 발표용 요약을 검사한다. 초기 병렬 검증에서 CPU 부하에 따라 SEND가 5초 제한에 걸린 실행이 있었으며 제한 자체는 유지한다. 전체 검증은 순차 실행해 확인했다. 실제 발표 PC에서 최종 리허설이 필요하다.

## 구조 설명과 독립 자동 재생 버튼

발표 포인트 영역을 구조 설명으로 교체했다. 세로셈과 공유 배정표, 제약 위반 시 분기 종료, 재귀 복귀 시 배정 해제, 합의 나머지·몫으로 결과 숫자와 올림을 전달하는 구조를 현재 장면에 맞춰 설명한다. 서버 장면의 해당 필드는 explanation이다.

장면 목차 옆에 자동 재생 버튼을 독립 배치했다. 재생 중 일시정지, 마지막에서 다시 자동 재생으로 바뀐다. 수동 이전/다음과 목차 이동은 자동 재생을 멈추며, 비교 패널은 각자 독립적으로 재생한다. 1×에서 장면당 약 6초, 5×에서는 약 1.2초다.

실제 I + BB = ILL 비교에서 왼쪽만 자동 재생해 2/10에서 일시정지, 재개 후 10/10에서 자동 정지, 다시 시작 후 1/10으로 복귀하는 것을 확인했다. 오른쪽은 계속 1/7을 유지했다. 구조 설명과 버튼을 포함한 패널 하단은 1280×720에서 약 699px로 화면 안에 들어왔다. 콘솔 오류는 없었다. [구조 설명과 자동 재생 화면](verification-assets/story-structure-auto.png).

검증: UI 전체 41개 통과. 구조 설명과 전용 재생 버튼, 재생·정지·종료·재시작·수동 이동 시 정지 회귀 테스트를 추가했다. Python 발표 장면 검증 2개와 요약 응답 지연 조회 검증 1개도 통과했다.
