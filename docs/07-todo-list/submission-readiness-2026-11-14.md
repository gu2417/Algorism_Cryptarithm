# 제출 및 발표 준비 상태 검증 (수정 전 이력)

이 문서는 문제 발견 당시의 상태다. 후속 조치와 최신 상태는 [수정 후 검증](remediation-verification-2026-11-14.md)을 참고한다.

검증일: 2026-11-14 (한국 시간). 대상: `feature/summary-playback`, 기준 커밋 `1d68ea7`에 현재 작업 폴더의 미커밋 변경을 포함한 상태. 로컬 서버 `http://127.0.0.1:5003`.

## 판정

**기본 기능 시연은 가능하지만, 현재 상태 그대로 최종 제출 및 발표 준비 완료로 판정하지 않는다.** 기본 예제의 완전탐색 미완료, 대량 응답, 문서와 실제 구현의 불일치가 남아 있다. 전체 테스트 통과는 현재 작성된 검증 조건을 만족한다는 의미이며, 모든 사용자 요청의 완료를 의미하지 않는다.

이번 작업은 검증과 보고다. 기존 소스의 기능 수정, PR 생성, 병합, 원격 이슈 등록은 수행하지 않았다. 검증 결과와 증거를 이 문서 및 `verification-assets/`에 추가했다.

## 검증 범위와 방법

- 최초 작업 지시서의 교육 목적·필수 기능, `docs/02-features/README.md`, 이후 사용자 요청을 대조했다.
- Python Core/API/통합/예제/페이지 테스트 27개 통과: `node_modules/qa-python/bin/python.exe -m unittest discover -s tests -v`.
- DOM 통합 테스트 27개 통과: `CRYPTARITHM_TEST_PYTHON`을 위 Python 경로로 설정한 뒤 `npm.cmd test`. 타이머와 네트워크를 제어하는 jsdom 테스트이며 실제 렌더링 검증과 구분한다.
- `node --check static/js/app.js`, `git diff --check` 통과. 줄바꿈 관련 Git 경고는 있었으나 diff 오류는 없었다.
- 별도로 난수 시드 `20261114`의 수식 80개를 만들었다. 단어 길이 1~3, 문자 A~D 범위에서 숫자 순열을 직접 열거한 독립 결과와 두 Core 알고리즘의 전체 해 집합이 모두 일치했다. 이 검증은 작은 문제 범위에 대한 증거이며 모든 입력의 수학적 증명은 아니다.
- 기본 예제 5개 × 알고리즘 2개를 실제 HTTP로 실행했다. 상태, 해 수, 기록 수, JSON 바이트 수와 응답 읽기 완료 시간을 측정했다.
- Chromium에서 실제 서버와 연결해 입력, 잘못된 연산자, 비교 패널, 개별 이전/다음·재생·정지, 재시작, 완료 안내, 전체/요약 전환을 확인했다. 확인 중 콘솔 오류는 없었다. Playwright MCP는 사용하지 않았다.
- 1280×720, 1920×1080, 375×812의 실제 화면을 확인했다. 비교 화면에서 문서 가로 너비는 각각 뷰포트 너비와 일치했다.
- README와 docs의 상대 Markdown 링크 검사: 끊어진 파일 링크 0개. 외부 URL의 연결 상태는 이 수치에 포함하지 않았다.
- 검증용 Python 환경의 `pip check`: 의존성 충돌 없음.

## 기본 예제 실측

실행 순서 및 컴퓨터 부하에 따라 값이 달라진다. HTTP 시간은 이번 로컬 요청 시작부터 응답 본문 읽기 완료까지이며 브라우저 렌더링은 포함하지 않는다. 원자료는 [측정 JSON](verification-assets/submission-audit-data.json)에 있다.

| 수식 | 알고리즘 | 상태 | 반환 해 | 내부 실행(ms) | HTTP(ms) | JSON 바이트 | 전체/요약 기록 |
|---|---|---|---:|---:|---:|---:|---|
| I + BB = ILL | 백트래킹 | 완료 | 1 | 3.87 | 57.18 | 182,535 | 879 / 56 |
| I + BB = ILL | 완전탐색 | 완료 | 1 | 25.67 | 111.74 | 544,647 | 2,723 / 42 |
| SEND + MORE = MONEY | 백트래킹 | 완료 | 1 | 427.67 | 1,876.39 | 16,926,299 | 74,211 / 56 |
| SEND + MORE = MONEY | 완전탐색 | 시간 제한 | 1 이상 | 5,000.04 | 8,231.86 | 17,877,357 | 80,000 / 49, 전체 절단 |
| A + A = A | 백트래킹 | 완료 | 1 | 0.42 | 152.92 | 18,858 | 71 / 24 |
| A + A = A | 완전탐색 | 완료 | 1 | 0.77 | 12.07 | 10,888 | 43 / 15 |
| A + B = C | 백트래킹 | 완료 | 32 | 4.80 | 36.44 | 160,717 | 804 / 56 |
| A + B = C | 완전탐색 | 완료 | 32 | 46.34 | 140.53 | 636,711 | 3,214 / 47 |
| A + B = AA | 백트래킹 | 완료 | 0 | 3.26 | 58.04 | 135,047 | 644 / 23 |
| A + B = AA | 완전탐색 | 완료 | 0 | 4.88 | 21.34 | 70,199 | 355 / 15 |

`SEND`의 반환 정답은 양쪽 모두 `9567 + 1085 = 10652`다. 완전탐색의 '1개 이상'은 중단 전 발견한 개수로, 전체 해 수를 확인한 결과가 아니다. 후속 실제 브라우저 비교 실행에서도 같은 완료/시간 제한 상태를 재현했다.

## 제출 전 해결해야 할 사항

### R01 높음: 대표 예제 완전탐색의 전체 탐색 미완료

재현: SEND 예제 → 완전탐색 또는 비교 → 풀이 시작. 5초 후 `time_limit`이 된다. 이전 직접 확인과 이번 HTTP/브라우저 확인에서 반복됐다. 정답 하나를 찾는 것과 모든 후보 탐색 완료는 다르다. 최초 설계에는 큰 입력 제한을 허용하므로 제한 자체가 정확성 결함은 아니지만, 이후 사용자가 요청한 대표 예제의 완전한 재생·완료 기대는 아직 충족하지 못한다. [실제 화면](verification-assets/send-compare.png).

수용 기준: 대표 예제를 어떤 조건으로 완료하거나 제한할지 명확히 하고, 기본 실행 경험이 그 기준을 만족하는 것을 실제 화면으로 입증해야 한다. 완료하지 않은 실행을 완료로 바꾸어 표시해서는 안 된다.

### R02 높음: 요약 보기의 대량 응답 문제

요약은 표시할 단계 수만 줄이며 API 응답의 `trace`와 `summary_trace`가 모두 반환된다. SEND 백트래킹 약 16.9MB, 완전탐색 약 17.9MB이며 비교 요청에는 양쪽이 합쳐진다. 측정상 내부 계산 시간 외 직렬화·전송 시간이 상당하다. 기록 한도를 늘린 것이 빠른 시연 요구를 충분히 해결하지 못했다. [원자료](verification-assets/submission-audit-data.json).

수용 기준: 요약 사용 시 실제 응답량과 화면 준비 시간도 줄어들고, 전체 보기는 필요할 때 접근할 수 있어야 한다. 비교 시 양쪽 준비 시간도 별도 검증해야 한다.

### R03 중간: 제한 중단 후 계산판과 정답 안내 불일치

재현: SEND 비교 실행 → 완전탐색 중요 요약을 마지막까지 다음으로 이동. 하단에는 발견한 정답이 나오지만 큰 계산판과 '지금 무슨 일이?'에는 마지막으로 선택된 후보/가지치기가 남는다. '끝나면 완성된 결과'라는 요청을 일부만 충족한다. [증거](verification-assets/send-compare.png)에서 왼쪽 완료 계산판과 오른쪽 제한 중단 계산판을 비교할 수 있다.

수용 기준: 마지막 후보와 발견한 정답을 화면에서 혼동 없이 식별할 수 있어야 한다.

### R04 높음: 제출 문서가 실제 구현 상태와 불일치

- `docs/02-features/README.md`: 모두 설계 단계라고 표기하며 비교 기록 전환 설명도 현재 동시 패널과 다름.
- `docs/04-file-structure/README.md`: 실제 코드가 생겼는데도 문서만 있는 상태와 구현 제안 구조를 설명. 현재 없는 `Common/`, `Feature/trace.py`, `Feature/compare.py`, `Kit/` 파일이 제안 트리에 남아 있음.
- `docs/07-todo-list/README.md`: T03 이후 대부분 미착수이며 마지막 문단에 실제 `??` 문자가 존재.
- `demo-draft.md`, `integration-verification.md`: 과거 10,000개 상한과 예전 테스트 개수 등이 남아 있음. 과거 보고서 자체는 이력으로 유효하지만 최신 제출 근거로 바로 사용하면 잘못 설명하게 됨.

수용 기준: 현재 구현, 미완료, 과거 이력을 구분하고 최신 실행 기준·파일 구조·테스트 수·발표 흐름이 일치해야 한다. 이번 검증 보고서는 기존 문서를 자동으로 최신화한 것으로 간주하지 않는다.

### R05 중간: 16:9 비교 화면의 정보 밀도와 스크롤

1280×720에서 두 계산판과 컨트롤은 보이나 단계 설명과 기록은 화면 아래에 위치한다. 1920×1080에서도 본문 최대 너비로 인해 두 패널이 각각 약 620px이고 글자가 작게 보인다. 좁은 화면의 페이지 가로 넘침은 없었다. 이는 기능 고장보다 발표 전달력 문제다. [1280 화면](verification-assets/stage-1280.png), [1920 화면](verification-assets/stage-1920.png), [모바일](verification-assets/compare-mobile.png).

수용 기준: 실제 발표 화면과 배율에서 계산·올림·단계 설명을 동시에 읽을 수 있는지 리허설해야 한다. 현재 '발표용 16:9 최적화 완료'로 쓰기는 어렵다.

### R06 중간: 독립 실행의 범위

UI의 개별 재생은 정상 확인했다. 예를 들어 왼쪽 다음을 누를 때 `1/56, 1/42`에서 `2/56, 1/42`로, 오른쪽 다음을 누르면 `2/56, 2/42`로 바뀐다. 왼쪽 자동 재생 중 오른쪽은 `1/42`에 머물렀다. 그러나 백엔드는 비교 요청에서 완전탐색과 백트래킹을 순차 계산한다. 각 알고리즘의 풀이를 따로 시작할 수 있다는 의미로 설명하면 현재 동작과 다르다.

## 발표에 사용할 수 있는 내용

- `I + BB = ILL` 비교는 두 알고리즘 모두 완료하므로 주 시연에 적합하다. 실제 정답 `1 + 99 = 100`, 완전탐색의 완성 배정 검사 576회와 백트래킹 1회를 이번 실행에서 확인했다. 이 값은 해당 문제의 측정이며 보편적 성능 배수로 일반화하면 안 된다.
- 백트래킹은 오른쪽 자리부터 합과 올림을 검사하고 결과 자리와 맞지 않거나 숫자 배정 제약을 어기면 가지치기한다. 완전탐색은 전체 배정 후 수식을 검사한다. 사용 숫자와 선행 0 제약은 양쪽 모두 적용하므로 '아무 제약도 확인하지 않는 완전탐색'이라고 설명하면 부정확하다.
- `A + B = C`로 32개 해와 선택 기능, `A + B = AA`로 해 없음을 짧게 보여 줄 수 있다.
- SEND 백트래킹은 확장 시연에 적합하다. SEND 완전탐색은 현재 '제한 중단과 부분 결과' 사례로만 설명할 수 있다.
- 실행 시간에는 기록 생성 비용이 포함되고 비교는 순차 실행이다. 순수 알고리즘의 공정한 성능 벤치마크라고 주장할 수 없다.
- 요약 56단계를 기본 500ms로 자동 재생하면 약 27.5초, 5배속은 약 5.5초다. 이는 타이머 간격으로 계산한 예상값이고 실제 5분 리허설 실측은 아니다. 발표에서는 자리 계산·올림·가지치기에서 멈추어 설명해야 한다.

## 환경과 미검증 한계

기존 `.venv/Scripts/python.exe`는 현재 PC에 없는 Python312 경로를 가리켜 실행되지 않았다. 이번에는 무시된 `node_modules/qa-python` 검증 환경을 명시적으로 사용했다. 이 현상만으로 README의 새 가상환경 생성 절차가 잘못됐다고 판정할 수는 없지만, 제출 전 새 PC 또는 깨끗한 가상환경에서 설치 절차를 확인해야 한다. 새로 clone한 저장소에서 전체 설치는 수행하지 않았다.

실제 스크린리더, 여러 브라우저·기기, 장시간 반복 사용의 메모리 누수·동시 부하, 외부 URL 전체 검사, 발표장 프로젝터, PPT·영상 결과물 및 실측 5분 리허설은 확인하지 않았다. 전체 페이지 캡처는 검증 도구의 sharp Windows 모듈 오류로 실패해 뷰포트 캡처를 사용했으며 이는 앱의 콘솔 오류와 다르다.

현재 코드 변경은 미커밋 상태다. 로컬에서 확인한 내용이 원격 develop이나 제출 브랜치에 반영되었다고 볼 수 없다. 위 사항 정리 후 PR과 제출 대상의 동일성을 다시 확인해야 한다.
